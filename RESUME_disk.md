## Where things stand (2026-10-07)

- **The CPU** (`rtl/DSPPC604/`) is unchanged since 0869a0f. Do not change it: if the machine finds a CPU bug or needs a CPU feature, stop, write `RESUME_cpu.md` for a CPU session, commit it, and stop. The lockstep run of the whole 7.6.1 boot to 497.8 million instructions agrees with dingusppc instruction for instruction, with one accommodation (the page table's R and C bits, below), so the CPU is not the suspect for what follows.
- **The bus error at "Welcome to Mac OS" is fixed.** It was the floppy controller's stub: the ROM's .Sony driver probes the SWIM3 (at 313 million instructions: interrupt mask <- 0, mode set 01, mode clear 18, phase <- 5, phase read back) and installs only if the phase lines read back; the stub read 0, SonyVars (low memory 0134) stayed -1, and Mac OS 7.6.1's System, loading, took the long before the Sony variables from the top of the ROM (084BF6D6) and dereferenced it: `CMPM.W (A2)+,(A0)+` at 497.8 million instructions. Found with the bench's new `--exc-log` and `--dump-at`/`--dump-bin` and confirmed to the byte by MacsBug 6.6.3 on the board. The fix: `rtl/machine/PPCMac_swim3.sv`, dingusppc's `swim3.cpp` register for register with one empty Superdrive (`superdrive.cpp`), on Grand Central's interrupt source 13, with a microsecond tick (`us_tick`) from `PPCMac_machine`. Lint clean, `run_scsi.py` passes, and on the board Mac OS now gets past the welcome screen.
- **The image runs with Virtual Memory on**: a 65 MB `VM Storage` file at its root, logical memory 0x04100000 (MemTop), 16 MB physical. The NanoKernel's page faults from 466.66 million instructions on are VM's, delivered to the 68k VM code (a DSI from the emulator whose `rfi` goes to 6806D358 is a bus error or page fault handed to the 68k; the kernel's own faulting access at FFF11518 or FFF11A10 comes first), and handled without disk I/O. Keep this in mind for every later fault: logical addresses above 16 MB are legitimate.
- **The hang at "Starting Up..." (the next problem).** On the board, with the SWIM3 built, 7.6.1 draws "Starting Up..." with its progress bar and stays there, the bar at its start, for minutes; the mouse moves the pointer. The debug readout (`cfg --uart debug`, `load`, `uart 4 --baud 115200`: row 0 the pc, 4 the MSR, 12 the device-write count) shows the CPU in the 68k emulator's handlers (68067F50, 680A5154, 680B0594...), MSR D076, the device writes growing by about 0x300 a readout: Mac OS's 68k code is looping, waiting for something. Mac OS 7.5.3 (`games/PPCMac/os753.hda`) stopped at the same screen *before* the SWIM3 was built, so the cause is probably not the floppy driver (though an empty drive's driver is a suspect too: it may wait for the drive's motor or ready line, which `PPCMac_swim3` answers as dingusppc's empty drive does). Mac OS 8.6 and 9.1 (`os86.hda`, `os91.hda`) stay on the grey screen before any welcome screen; 9.1 was seen earlier with the CPU in the SCSI Manager.
- **The hang reproduces in simulation** (`~/.cache/ppcmac/buserr_e.log` and `buserr_e_exc.log` in WSL, 800 million instructions, no lockstep, no device log): the welcome screen at 500 million, "Starting Up..." drawn by 783 million, and from 700 million on the CPU is in *native* PowerPC code in RAM, user mode (MSR D072), at 0019A5F4-0019A664 and 0021B0D4 (the progress line's pc at every 25 million from 700 million), with 14 external interrupts and 11 kernel calls per million instructions and no page faults: a native fragment polling something, not the 68k emulator. So the first thing to do is `--trace-from 750000000 --trace-count 3000` (and `--dump-at 750000000 --dump-bin ...`) on a run to 750 million with `--dev-log`: the loop's instructions, the device it reads, and the fragment's name (CFM fragments carry their names; `ramdump.py find` with the hex of a name). Native code at that stage is a native driver or library the System loaded: the Sound Manager's, the serial driver's, the display's.
- **The board's state**: `_Unstable/PPCMac.rbf` is the build with the SWIM3 (28,437 ALMs, 68 %; the CPU's clock closes at 60.4 MHz slow 100 C in this fit, runs at 65); `games/PPCMac/boot.rom` the 7300's ROM; on the card `os761.hda` (mounted as SCSI disk 0 by `config/PPCMac.s0`), `os761mb.hda` (the same with MacsBug 6.6.3 in its System Folder), `os753.hda`, `os86.hda`, `os91.hda`; options default; the menu core loaded. ## Rules

- SystemVerilog, limited to what Verilator 5.020 and Quartus 17.0 both accept; Verilator `-Wall` clean (`make -s lint` in `verilator\`; it takes the machine's file list from `rtl/machine/PPCMac_machine.qip`, so a new file goes there; the SCSI bench's top is linted too and instantiates `PPCMac_gc`, so a new Grand Central port needs a value there). Quartus 17 refuses, silently or not: a second read expression on a memory, byte-enabled writes to a wide array, a variable part-select or bit-select of a two-dimensional array, `genvar` inside the `for`, a generate loop without `generate`, every RAM style attribute, a three-input add or subtract as one expression, a RAM written from registers with a combinational read. Watch for signed constants that overflow. In Verilator a size cast of a signed expression inside a function call's argument did not sign-extend as written: write sign extensions out.
- Machine modules are `PPCMac_*` under `rtl/machine/`. `sys/` is never edited.
- Real hardware outranks every emulator; of the emulators dingusppc is trusted most; where dingusppc is high-level or missing, Linux's drivers and the chips' manuals; Apple's own firmware is evidence too (`rom7300/`).
- Edit files with the editor tools (Edit, Write), not scripts, `sed` or heredocs. Generated files and files copied whole from my other repositories are the exception.
- Commit at verified points with explicit paths (never `git add -A`), messages through a file (`git commit -F`), ending with the co-author line the harness gives. Never push or add a remote. Do not modify anything under `ppctest\` (another session's; running its tools is fine) or the dingusppc tree. Quartus rewrites a line of `PPCMac.qsf`; leave it out of commits. `Scratch\` is git-ignored.
- Update `docs/PPCMac_stubs.md` in the same commit as any change to a stub.
