# PPCMac: what is stubbed

Everything the machine fakes, simplifies or leaves out, in one place, so that
none of it surprises us later. Every entry says what the stub does now, what
the real hardware (and dingusppc, our reference) does instead, and what is
likely to need the real thing. Update this file in the same commit as any
change to a stub. An entry leaves this file only when the real behaviour is
built and tested; the commit that does it says so.

Sources: `rtl/machine/` (the RTL), dingusppc's `machines/machinetnt.cpp` and
the device files it names (the reference). "Reads 0" means every register of
the device reads as zero and writes are ignored.

## Machine level (`PPCMac_machine.sv`, `PPCMac_system.sv`)

| What | The stub | The real thing | Will need it |
|---|---|---|---|
| Bus errors, machine check | Never. Every access is acknowledged (at once, or for the VIA when its clock allows: below); a device that is not there reads 0. | A real 7600 can raise a machine check (TEA) for some unmapped accesses; dingusppc raises one for PCI I/O space with no device. The CPU has no machine-check exception yet. | Anything that probes for hardware by catching the machine check. Measured: RAM space beyond the installed memory does not need it. |
| RAM beyond the installed size | Reads 0, writes ignored. | The same on the 7300 (measured). dingusppc reads all ones. | Nothing known. |
| Line (cached) accesses to devices | Eight word accesses to the device, the lowest address first, as a burst on the real bus would be (the ROM reads Hammerhead's CPU ID through the data cache before it sets up any BAT: with data translation off the 604 caches everything). Outside any device: zeros. | A real device sees a 4-beat burst of 8 bytes; how each device answers a burst is not documented. Hammerhead's ID register gives the right answer either way. | A device with read side effects (VIA, SCC) read through the cache would see eight reads here; nothing does that so far. |
| Debug registers at F9000000 | Not a 7600 device: 256 bytes where the memory test reports (status, passes, errors, first error, the word read and expected; installed RAM size, read only). The debug readout shows them. | Nothing at that address on a 7600 (it would read 0). | Remove or move it if any software probes F9000000. |
| Memory-test boot program | With the OSD's Boot option at "Memory test", an 8 KB program in block RAM (`PPCMac_bootrom.sv`, generated by `progs.py memtest`) answers for the ROM's 4 MB, mirrored. | - | - |
| Writes to the ROM | Ignored. | Ignored (ROM). | - |
| PCI base address registers | Stored and read back, but the decoder does not follow them. Grand Central is fixed at F3000000, where the 7600's ROM puts it. | The bridges route accesses to wherever the BARs point. | A ROM or OS that moves Grand Central; any PCI card. |
| Hammerhead bank base registers | Stored and read back. RAM is mapped flat from 0 at the installed size whatever they say. | The real Hammerhead maps each DIMM bank at its base. dingusppc maps flat, as here. | Software that relies on banks not being contiguous (none known). |
| Other memory masters (DMA) | None. The CPU's snoop port is tied off. | Grand Central's DBDMA engines (sound, SCSI, serial, floppy, Ethernet) and PCI masters read and write memory. | Startup chime, SCSI, floppy, serial DMA. |
| External interrupt | Grand Central's output. Its sources so far: the VIA (2026-10-07), Curio and MESH (milestone E). | VIA, SCC, SCSI, DMA and PCI interrupts through Grand Central. | Each source comes with its device (`docs/PPCMac_plan.md`, milestone I). |
| VIA access time | Modelled as MAME's Grand Central has it (heathrow.cpp `via_sync`): a word access to F3016000-F3017FFF waits for the next edge of the VIA's 783,360 Hz clock and then half a cycle, 0.64-1.91 us. A line access to the VIA goes at once. | Grand Central's VIA cell, synchronised to its clock; not measured on a 7600 (`hwprobe/` times 1000 reads of port B and of IFR on the 7300, and of other Grand Central registers beside them; waiting for a run). | Already needed: the ROM's Cuda timeouts are counts of VIA reads, and after each byte it waits ten VIA reads (FFF04BCC) for Cuda to sample the byte's last bit 3.8 us after the VIA's flag. Answered at once, the ROM corrupts that bit. Mac OS calibrates its delays (TimeVIADB) on VIA accesses too. |
| The CPU's reset | Cuda (PC3) holds it from the machine's reset until its firmware has powered the machine up: every start is the firmware's cold start, as after a battery is put in: about 1.0 s on the 16 kHz crystal clock, the PLL on, then 250 ms of power-on sequence (1.28 s in all on the board). A restart (PC3 low again) resets the CPU only. | Cuda runs from the battery all the time; the power key starts the machine in about 250 ms. A restart resets the whole board. | A faster start if wanted (Cuda's state could be saved). A restart that relies on Grand Central and the bridges being reset too. |
| Second CPU, L2 cache, Bandit 2 | Absent (Hammerhead reports one CPU and no L2; the board ID has no second PCI bus). | As configured on a 7600. | - |

## Grand Central, the I/O controller (F3000000, `PPCMac_gc.sv`)

| What | The stub | The real thing | Will need it |
|---|---|---|---|
| Interrupt registers | Events, mask, clear and levels as MAME's Grand Central (`heathrow.cpp` `set_irq_line`) and dingusppc's (`ack_int_common`) have them: an event at a line's rising edge, or at either edge in 68k mode (the mask's top bit); levels are the lines, with bit 11 set as dingusppc sets it. Connected: Curio (0C), MESH (0D), the VIA (12). Not modelled: dingusppc's clearing of DMA levels through the clear register (`clear_dma_int`), there being no DMA interrupt yet. | Every device below raises events. Not measured on a real machine; MAME and dingusppc agree. | The other sources, with their devices. |
| VIA interrupt, re-signalled | The VIA's line changes only when IFR & IER does, as a 6522's IRQ pin and MAME's 6522 (`output_irq`). | dingusppc's VIA calls Grand Central on every register access while its interrupt is active (`viacuda.cpp` `update_irq`), and in 68k mode each call is a new event: dingusppc takes interrupts a real line could not cause (from 65 million instructions, around Mac OS's Cuda transfers). | Nothing: the device traffic against dingusppc differs only by those extra interrupts. |
| DMA channel registers (DBDMA) | Channels 0-3, 8 and A store their registers and read them back; RUN and PAUSE follow writes; ACTIVE is never set and no command is ever fetched. Channels 4-7 (serial) and 9 (sound in) read 0, as in dingusppc. | Each channel runs a program of descriptors from memory (dbdma.cpp). | The startup chime (sound out, channel 8): its command list and samples are in the ROM (the `beep` resource at FFE00010 on; `rom7600/README.md`), so the DMA engine must be able to read the ROM as well as RAM. Then SCSI, floppy. |
| VIA | Registers implemented; T1 and T2 count at 783,360 Hz and set their flags as dingusppc's do; the interrupt (IFR & IER) is Grand Central's source 12 (2026-10-07). Port B is a 6522's (the output register holds all eight bits; PB3 reads Cuda's TREQ, the other input pins 0); the shift register is clocked by Cuda on CB1 in the two modes Cuda's protocol uses (shift out under CB1, 111; shift in under CB1, 011), as MAME's 6522 does them: the flag at the eighth falling edge out, the eighth rising edge in. Port A, the CA1/CA2/CB1/CB2 flags and the other shift modes are not modelled (Mac OS enables only T2 and the shift register's interrupts, `vIER` A0 and 84). | A 6522 cell with Cuda on port B and the shift register, its interrupt Grand Central's source 12. | Anything that enables the CB1 or CA flags. |
| Cuda | The chip itself: see its own section below. | - | - |
| ESCC (serial) | `PPCMac_escc.sv` (2026-10-07): a Z85C30's asynchronous mode. Channel A, the modem port, is the MiSTer's UART (OSD: UART = Modem port), transmitting and receiving at the rate the baud-rate generator is set to (RTxC 3.6864 MHz; Open Firmware: 38,400 baud, 8 bits, 2 stop bits); RR0's receive and transmit-buffer bits, RR1's all-sent, a three-byte receive FIFO. Channel B has the same registers and no line. Left out: interrupts (sources 0F, 10), DMA (channels 4-7), the synchronous modes, the DPLL, CRC, break, the modem lines (RR0 otherwise reads 44, CTS and DCD 0, as dingusppc), PCLK (taken to be RTxC), and the read registers dingusppc does not keep (only RR0, RR1, RR2 = WR2 and RR8 answer). One and a half stop bits are sent as two. | Two Z85C30 channels (escc.cpp: transmits at once, RR0 always "empty"). | Mac OS's serial driver (interrupt-driven); the printer port. |
| AWACS (sound) | Control, codec control, clip count, byte swap and frame count registers stored as in dingusppc; codec status reads 00314000 (available, Crystal, Screamer). No sound. | A codec fed by DMA channel 8. | The startup chime. |
| NVRAM | 8 KB, implemented, through the address-high latch at 1D000 and the data window at 1F000. Zeros when the core is loaded, as dingusppc without a file, unless `games/PPCMac/boot1.rom` holds an image, which the core loads at its start (`syn/nvram_of_prompt.bin`: Open Firmware's own defaults with `auto-boot?` false; `verilator/nvram.py` makes and changes such images). A reset leaves it as it is; nothing is saved. | Battery-backed: keeps Open Firmware's settings. | Keeping settings across a power-off (milestone P: the save to the SD card). |
| Board register 1 | E13F, as dingusppc builds it for a 7600 (no composite video, fast SCSI present, factory tests off). | The same, from the board. | - |
| Ethernet address ROM | 08 00 07 44 55 66 00 00 (dingusppc's made-up address). | The machine's own address. | Networking. |
| Curio SCSI (53C94) | `PPCMac_sc53c94.sv` (milestone E): the Am53CF94 cell's registers, read and write maps apart, as dingusppc's `sc53c94.cpp`; the two-deep command FIFO; the 16-byte data FIFO; reset chip, reset bus (RST for 25 us; the interrupt unless configuration 1 disables it), clear FIFO, no operation, reset ATN, enable selection, and the three selections, which on the empty bus end in a disconnect interrupt after the selection timeout; the extended transfer count with ENF, the part ID (0C, dingusppc's) in it after a chip reset; the interrupt line, Grand Central's source 0C. Left out: targets, the information phases (transfer, command complete, message accepted, transfer pad: an invalid-command interrupt here, as on a 53C94 that is not connected; dingusppc stops), DMA and the pseudo-DMA port, reselection, the target-mode commands, parity, the phase latch (no target ever drives a phase), the synchronous period and offset (written, unused). | The external SCSI controller (sc53c94.cpp). | External SCSI devices. |
| Curio's selection timeout | 8192 x the clock conversion factor x the timeout register, in the chip's clocks (the 53C94's formula, as MAME's `ncr53c90.cpp`), the chip's clock taken to be 25 MHz (`SCSI_HZ`): the ROM's factor 5 and timeout A7 make 273.6 ms. | Unknown: the clock Curio's SCSI cell runs at on a 7300 is not documented here; factor 5 means 20-25 MHz. dingusppc waits a fixed 250 ms. | `hwprobe/` (built 2026-10-07, waiting for a run on the 7300) times a selection of an empty ID at two timeout values, which gives the clock. |
| MESH SCSI | `PPCMac_mesh.sv` (milestone E): the registers as dingusppc's `mesh.cpp` (the ID E2, the transfer count, the sequence register, bus status 0 and 1 driving and reading the lines, exception, error 0, interrupt and mask, destination ID, synchronous parameters, the selection timeout); arbitrate, select, bus free, reselection on and off, reset MESH, flush FIFO, parity on and off, with dingusppc's bus-controller timing (`scsibusctrl.cpp`: 1,200 ns until arbitration, 2,400 ns of it, won), and with no target a selection timeout after the register's value x 10 ms (the ROM writes 0x19: 250 ms, dingusppc's fixed `SEL_TIME_OUT`; the ROM computes it as milliseconds / 10, `nitt` 43 at FFEB7C1C); the interrupt line, Grand Central's source 0D, as any unmasked interrupt bit. Left out until S: the FIFO (reads 0, writes ignored), the information phases (they only clear command done), DMA (channel 0A), reselection, targets, parity. The exception register is cleared as dingusppc clears it (arbitrate keeps only arbitration lost, select only selection timeout); arbitration is never lost (MESH is alone on the bus). | The internal SCSI controller, our boot disk path (mesh.cpp). | Booting from disk (milestone S). |
| MESH's interrupt line | Follows the interrupt and mask registers at all times, as a chip's pin. | dingusppc recomputes it only at some events, not after reselection on and off, which set command done: there its line can rise a few hundred instructions later (at the next mask write) or not at all (a select clears command done first). In 68k mode each edge is a Grand Central event, so the two can differ in an event no one sees until the mask is enabled. Not measured on a real machine; the 34F2 ROM issues reselection off (0D) just before each select. | `hwprobe/` (waiting for a run on the 7300) reads the interrupt register after 0D, after 0F and at once after a select, and times MESH's selection timeout at 0x19 and 0x05. |

| SWIM3 floppy | Reads 0. | swim3.cpp. | Floppy. |

| IOBus devices 3, 5 | Read 0. | Absent on a 7600 too (sixty6 and board register 2 belong to other models). | - |

## Cuda (`PPCMac_cuda.sv`, `PPCMac_hc05.sv`)

The microcontroller itself: a 68HC05E1 (`PPCMac_hc05`, every instruction
and its cycle count checked against MAME's 6805 core) running Apple's
firmware 341S0060, Cuda 2.40, from MAME's dump (`rtl/machine/cuda/`), on
its 2,097,152 Hz bus. What is left out around it:

| What | The stub | The real thing | Will need it |
|---|---|---|---|
| Which Cuda | 341S0060 (2.40). | **The same.** Read out of the 7300's chip through the VIA on 2026-10-07 (`cudadump\`, READ_MCU_MEM from Open Firmware, 604 card): ROM 0F00-1FFF is 341S0060, Cuda 2.40, byte for byte the file built in (CRC32 0F5E7B4A; copyright "(c) 1989-94 Apple Computer, Inc." at 0F00, version words 0010 0002 0028 at 0F36). 0B00-0EFF read back the low byte of the address: nothing there, a 68HC05E1's open bus (the RTL reads 0 for unmapped addresses; the firmware never reads them). MAME's notes put 341S0060 in the PCI x500 machines, the Pippin and the 6200 too; the 7600's board (dead) showed no label. | Nothing. |
| ADB | Nothing on the line: Cuda's own drive is all there is. An ADB talk gets no answer (Cuda replies 00 06 cmd). | A keyboard and a mouse (dingusppc attaches both by default, so its Mac OS's ADB traffic differs from ours). | Input. The Mac LC core's `adb_device.sv` (keyboard and mouse on the ADB wire, from the MiSTer's PS/2) is the candidate. |
| I2C | Nothing on Cuda's I2C lines (pulled up). The ROM's first packet, a write of 61 55 to address 88, gets Cuda's I2C error (02 05 01 22). | Something at 88 on a 7600, not known what. dingusppc has nothing there either and answers the same error. | Whatever that device is. |
| PRAM and the clock | The firmware's cold start: PRAM (MCU RAM 100-1FF) zeroed, the clock at 630BD178 (1956) and counting. Nothing kept across a reset, nothing set from the MiSTer's clock. | Kept by the battery. The 7300 on 2026-10-07: PRAM (0100-01FF) all zero, the clock 7C26C24C (1970-01-01 19:28) and counting (two reads two seconds apart). | The date and time in Mac OS (MAME loads both when Cuda first releases the reset: cuda.cpp pc_w). On a 7600, Mac OS's XPRAM is in Grand Central's NVRAM (1300-13FF), so Cuda's PRAM matters less. |
| Power | Straps for soft power with the power key and the power button up (PA5, PA1, PA2 = 1; MAME reads PA5 as 0, which with RTI makes the firmware power down 125 ms after powering up). Nothing switches a power supply: a power-off (not tried yet) would put Cuda in its power-down loop and leave the CPU running. The IRQ pin is high (unused), NMI (PC2), fast reset (PA3) and the DFAC latch (PA4) go nowhere. | The power supply, the keyboard's power key, the front button, the NMI switch. | Shut Down and Restart from Mac OS (restart through PC3 works now). |
| The timer, the clock source | TOF at the bus clock / 1024, RTI at 2^(14 + RT) bus cycles, the one-second interrupt from the crystal; the bus from the crystal (16,384 Hz) until the firmware selects the PLL, then the PLL's rate (2,097,152 Hz). The PLL switches at once. | The same, the PLL taking a few ms to lock. MAME has no RTI and no slow clock. | - |

## Things the ROM measures that a slower machine changes

- The bus clock: VIA timer 1 measured against the decrementer, so the
  decrementer must run at bus clock / 4 (12.5 MHz, `TB_HZ`) against the VIA's
  783,360 Hz. Both are made exactly by phase accumulation in `PPCMac_machine`.
- The CPU clock: a decrementer-timed loop of eight dependent `addi` and a
  `bdnz`, assuming one instruction a clock. This core, slower per clock than
  a 604, will report a lower CPU clock to Open Firmware and Mac OS. That is a
  true reading of its speed, not a stub; noted so that it does not surprise.
  (Both from `rom7600/README.md`.)

## Not on the bus at all yet

- The modem port's handshake lines (the MiSTer's UART has RTS and DTR tied
  low, CTS and DSR unused).
- ADB keyboard and mouse (Cuda is built; its ADB line has nothing on it).
- Video output of the machine (the MiSTer screen shows the debug readout).
- Sound output.
- Disk images (SCSI through MESH, floppy through SWIM3).

## The lockstep bench's accommodations (`verilator/core_main.cpp`, machine mode)

Not stubs in the machine, but places where the comparison with dingusppc
takes the core's word for something, so a fault there would not show up as a
lockstep mismatch:

- A device read in the reference returns the value the core's machine
  returned (the reference has no devices of its own). The reads are checked
  to happen in the same order, at the same address and size; writes are
  checked for address, size and data.
- `mftb`, `mfspr` of the time base and `mfdec` give the core's value.
- The decrementer and external interrupts are taken in the reference where
  the core took them.
- `mtspr` and `mfspr` of an SPR the real 604 does not have (the README's
  list): the core takes the program exception (illegal) as the chip does;
  dingusppc accepts the 604e's MMCR1, PMC3 and PMC4, which the NanoKernel
  probes (FFF131B0 on), so the reference is made to take the exception
  with the core's SRR0, SRR1 and MSR.
- MSR[PM] (bit 29, which the 604 keeps: measured) through `rfi` and
  exception entry: a 604 copies SRR1's low 16 bits into MSR on `rfi` and
  MSR's into SRR1 on an exception, PM among them; dingusppc leaves PM out
  of both (`ppc_rfi` replaces 0x87C0FF73, `ppc_exception_handler` keeps
  0x0000FF73). The NanoKernel returns to Mac OS with PM set (FFF12C50,
  33.2 million instructions) and Mac OS traps with it set, so the
  reference's MSR takes PM from SRR1 after every `rfi`, and its SRR1 takes
  PM from the MSR at every exception and injected interrupt. Not
  machine-mode only: the 604's rule holds in the CPU suite too.
- A DSI at `dcbst`, `dcbf`, `icbi` or `dcbi`: the core translates them as
  loads (`dcbi` as a store), as the architecture and the 604 do; dingusppc
  does not translate them at all. The NanoKernel fills the hardware page
  table on demand, so when Open Firmware's flush word, called from Mac OS,
  runs `dcbst` over code it has just compiled (FF808D14, 33.2 million
  instructions, DAR FF840940, DSISR 40000000), the real machine takes the
  same DSI and the NanoKernel installs the PTE and retries. The reference
  is made to take it (SRR0, SRR1, DAR from its own state; DSISR "no
  translation", or the protection bit when dingusppc's MMU does translate
  the address, which the handler's read of DSISR then checks).
- Cuda's clock runs 15 times fast while it holds the CPU in reset
  (`CUDA_FAST_BOOT`, the machine bench's build only), so the cold start
  takes 5.4 million cycles, not 83 million. Cuda's instructions are the
  same; only its clock (and so its real-time clock) is ahead.

And Cuda's own bench (`verilator/cuda_main.cpp`, `run_cuda.py`): MAME's
6805 core is handed the values the RTL read from the registers (0000-001F)
and takes interrupts where the RTL took them; the VIA and the host there
are models (MAME's 6522 shift register, Linux's via-cuda.c protocol paced
as the 7600's ROM paces it), not the 7600's RTL or ROM.
