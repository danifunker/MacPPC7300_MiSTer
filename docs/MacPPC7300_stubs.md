# MacPPC7300: what is stubbed

Everything the machine fakes, simplifies or leaves out, in one place, so that
none of it surprises us later. Every entry says what the stub does now, what
the real hardware (and dingusppc, our reference) does instead, and what is
likely to need the real thing. Update this file in the same commit as any
change to a stub. An entry leaves this file only when the real behaviour is
built and tested; the commit that does it says so.

Sources: `rtl/machine/` (the RTL), dingusppc's `machines/machinetnt.cpp` and
the device files it names (the reference). "Reads 0" means every register of
the device reads as zero and writes are ignored.

## Machine level (`MacPPC7300_machine.sv`, `MacPPC7300_system.sv`)

| What | The stub | The real thing | Will need it |
|---|---|---|---|
| Bus errors, machine check | Never. Every access is acknowledged (at once, or for the VIA when its clock allows: below); a device that is not there reads 0. | A real 7600 can raise a machine check (TEA) for some unmapped accesses; dingusppc raises one for PCI I/O space with no device. The CPU has no machine-check exception yet. | Anything that probes for hardware by catching the machine check. Measured: RAM space beyond the installed memory does not need it. |
| RAM beyond the installed size | Reads 0, writes ignored. | The same on the 7300 (measured). dingusppc reads all ones. | Nothing known. |
| Line (cached) accesses to devices | Eight word accesses to the device, the lowest address first, as a burst on the real bus would be (the ROM reads Hammerhead's CPU ID through the data cache before it sets up any BAT: with data translation off the 604 caches everything). Outside any device: zeros. | A real device sees a 4-beat burst of 8 bytes; how each device answers a burst is not documented. Hammerhead's ID register gives the right answer either way. | A device with read side effects (VIA, SCC) read through the cache would see eight reads here; nothing does that so far. |
| Debug registers at F9000000 | Not a 7600 device: 256 bytes where the memory test reports (status, passes, errors, first error, the word read and expected; installed RAM size, read only). The debug readout shows them. | Nothing at that address on a 7600 (it would read 0). | Remove or move it if any software probes F9000000. |
| Memory-test boot program | With the OSD's Boot option at "Memory test", an 8 KB program in block RAM (`MacPPC7300_bootrom.sv`, generated by `progs.py memtest`) answers for the ROM's 4 MB, mirrored. | - | - |
| Writes to the ROM | Ignored. | Ignored (ROM). | - |
| PCI base address registers | Stored and read back. The decoder follows Control's two memory BARs (registers, VRAM; milestone V), whatever the command register says (as dingusppc); the others it does not follow: Grand Central is fixed at F3000000, where the ROM puts it. | The bridges route accesses to wherever the BARs point. | A ROM or OS that moves Grand Central; any PCI card. |
| Hammerhead bank base registers | Stored and read back, and they place the RAM: one bank for each power of two in the RAM option (120 MB: 64, 32, 16 and 8 MB in banks 0-3), each answering only within its size at its base (no mirror above it). Flat from 0 until the ROM sets a base. | The real Hammerhead maps DIMM banks of any size the ROM finds (and their "size bit"); real banks may mirror above their size. dingusppc maps flat. | Flat RAM let the ROM find a bank of 56 MB at 64 MB and cut it to 32: 120 MB came up as 96 (2026-10-08). |
| Other memory masters (DMA) | Grand Central's DBDMA engines (2026-10-08: channels 2 and 3, Ethernet out and in; 8 and 9, sound out and in; A, MESH's), one access at a time through an arbiter in `MacPPC7300_gc` (the sound channels first, then MESH, then Ethernet), into `MacPPC7300_machine`'s DMA port: each access's line through the CPU's snoop port first (written back if dirty, dropped for a write), then the memory port, before any new CPU access; a write's line is snooped a second time after it, dropping any copy a cache fetched between its part of the first snoop and the write (the CPU's accesses cannot wait during a snoop: a cache may have to finish a fill before it answers). Not covered: a CPU store into such a copy in those few clocks would be written back over the DMA's bytes (a store to the same 32-byte line as an incoming DMA, in a window of some 20 clocks). A DMA access outside RAM and the ROM reads 0 and writes nothing. | Grand Central's DBDMA engines (sound, SCSI, serial, floppy, Ethernet) and PCI masters read and write memory; the 604 snoops each bus transaction as it happens (ARTRY), so a transaction and its snoop are one. | The serial channels (4-7) and Curio's and the floppy's (0, 1), if their devices ever move data. A CPU whose caches hold off fills while a snoop is pending would close the window (a CPU change). |
| External interrupt | Grand Central's output. Its sources so far: the VIA (2026-10-07), Curio and MESH (milestone E), the Control video's VBL (1A, milestone V), the SWIM3 (13), and from 2026-10-08 the DMA channels 2, 3, 8, 9 and A, MACE (0E), the ESCC's two channels (0F, 10) and Cuda's NMI (14). | VIA, SCC, SCSI, DMA and PCI interrupts through Grand Central. | AWACS's own (11), the PCI slots' (17-19). |
| VIA access time | Modelled as MAME's Grand Central has it (heathrow.cpp `via_sync`): a word access to F3016000-F3017FFF waits for the next edge of the VIA's 783,360 Hz clock and then half a cycle, 0.64-1.91 us. A line access to the VIA goes at once. | Grand Central's VIA cell, synchronised to its clock; not measured on a 7600 (`hwprobe/` times 1000 reads of port B and of IFR on the 7300, and of other Grand Central registers beside them; waiting for a run). | Already needed: the ROM's Cuda timeouts are counts of VIA reads, and after each byte it waits ten VIA reads (FFF04BCC) for Cuda to sample the byte's last bit 3.8 us after the VIA's flag. Answered at once, the ROM corrupts that bit. Mac OS calibrates its delays (TimeVIADB) on VIA accesses too. |
| The CPU's reset | Cuda (PC3) holds it from the machine's reset until its firmware has powered the machine up: every start is the firmware's cold start, as after a battery is put in: about 1.0 s on the 16 kHz crystal clock, the PLL on, then 250 ms of power-on sequence (1.28 s in all on the board). A restart (PC3 low again) resets the CPU and, since 2026-10-08, the board's devices with it (the bridges, Grand Central and everything behind it, the Control video, the disks' bus side; not Cuda, the ADB devices, Athens or the NVRAM's contents), as a real restart does: no sound DMA or device state survives a Mac OS Restart. | Cuda runs from the battery all the time; the power key starts the machine in about 250 ms. A restart resets the whole board. | A faster start if wanted (Cuda's state could be saved). |
| Second CPU, L2 cache, Bandit 2 | Absent to the software (Hammerhead reports one CPU and no L2: register 0E reads 0; the board ID has no second PCI bus). The machine does have an L2 since 2026-10-08 (`MacPPC7300_l2.sv`: 128 KB, direct-mapped, write-back, on the memory port in front of the clock crossing, OSD "L2 cache (on reset)"), but it is not reported: the ROM's L2 code (FFF03D48) wants bit 7 of 0E, then a word read of 0E after writing 70 to it and 80 to 0F whose bits 13-12 give the size, then reads the L2's size of RAM to flush it; what a real Hammerhead returns to that word read is not known (dingusppc returns 0 too). | The 7300's 256 KB cache DIMM; Hammerhead's 0E says so. | Apple System Profiler showing the L2 (cosmetic); the real 7300 can be asked what 0E reads. |

| Control's VRAM | 4 MB (both banks fitted, as dingusppc's default) in the HPS's DDR3 at byte 3000_0000, through its own clock crossing and the framework's DDRAM port (`MacPPC7300_video`); the apertures as `control.cpp`: big-endian at window offset 800000, little-endian below with the bytes swapped within each pixel; in wide mode the window's low 4 MB, otherwise bits 22-21 pick a bank (3 the optional). Simplified: in narrow mode a write to bank region 1 goes to the standard bank only (dingusppc also writes the optional bank there); the bank configuration is fixed; every CPU access waits for DDR3 (no posted writes); the power-up contents are whatever the DDR3 held. | Two banks of VRAM behind Control (2 MB each), 64 or 128 bits wide. | Mac OS's driver uses wide mode only (MISC_ENABLES 51). |
| The picture | Control's scan-out at the dot rate Athens sets (a clock enable of the 100 MHz memory clock), through the framework's scaler (HDMI) and its analog output; the OSD picks it or the debug readout, and the monitor: the 16-inch RGB (832 x 624, the default) or the 13-inch (640 x 480). 8 bits a pixel through RaDACal's colour table; 32 bits each component through its own column of the table (DirectColor, 2026-10-08: Linux's controlfb keeps its console colours there, pixel 07-07-07 for its grey, which showed almost black without it; Mac OS loads a linear ramp); 16 bits direct, without the table (as dingusppc). The hardware cursor from the 16 bytes before each line, at RaDACal's position (bit 3: the cursor colour; bit 0 alone: inverted). | The same at the monitor's own pixel clock, the direct modes through the gamma table. | 16-bit DirectColor through the table, if software needs it (how RaDACal indexes it with 5-bit components is not known here). |
| Sub-word configuration accesses | Only aligned word writes are modelled (reads of any size are right). | dingusppc converts byte and halfword accesses. | Nothing seen yet. |

## Grand Central, the I/O controller (F3000000, `MacPPC7300_gc.sv`)

| What | The stub | The real thing | Will need it |
|---|---|---|---|
| Interrupt registers | Events, mask, clear and levels as MAME's Grand Central (`heathrow.cpp` `set_irq_line`) and dingusppc's (`ack_int_common`) have them: an event at a line's rising edge, or at either edge in 68k mode (the mask's top bit); levels are the lines, with bit 11 set as dingusppc sets it. Connected: the DMA channels 02, 03, 08, 09 and 0A (each a level from the channel's interrupt until the clear register's bit drops it, as dingusppc's `ack_dma_int` and `clear_dma_int`; in 68k mode the drop is an event), Curio (0C), MESH (0D), MACE (0E), the ESCC's channels A and B (0F, 10), the VIA (12), the SWIM3 (13), Cuda's NMI (14: `AppleGrandCentral`'s nmiSource, dingusppc's `IntSrc::NMI`), the Control video's VBL (1A). | Every device below raises events. Not measured on a real machine; MAME and dingusppc agree. | AWACS's (11), with its port-change and error conditions. |
| VIA interrupt, re-signalled | The VIA's line changes only when IFR & IER does, as a 6522's IRQ pin and MAME's 6522 (`output_irq`). | dingusppc's VIA calls Grand Central on every register access while its interrupt is active (`viacuda.cpp` `update_irq`), and in 68k mode each call is a new event: dingusppc takes interrupts a real line could not cause (from 65 million instructions, around Mac OS's Cuda transfers). | Nothing: the device traffic against dingusppc differs only by those extra interrupts. |
| DMA channel registers (DBDMA) | Channels 2, 3 (Ethernet out and in, to MACE), 8, 9 (sound out and in, to AWACS; 2026-10-08) and A (MESH's, milestone S) are each a `MacPPC7300_dbdma.sv`: the channel's registers and its programs as `dbdma.cpp` runs them (INPUT and OUTPUT MORE and LAST, STORE and LOAD QUAD, NOP, STOP; the wait, branch and interrupt conditions; resCount and xferStatus written back; RUN, PAUSE, WAKE, FLUSH), reading commands and data from RAM or the ROM and writing RAM. The device's status bits (2026-10-08, from Mac OS's MACE driver on the board): channel 2's s5 is MACE's transmit status valid (XMTSV; the driver's OUTPUT_LAST waits on it, w2 with wait select 0x0020/0x0020); on channel 3 MACE's end of frame ends an INPUT_MORE as well as an INPUT_LAST (the driver gives it 1,536-byte INPUT_MOREs with interrupt always) and s6 reads 1 while that command finishes (NetBSD's if_mc tests xferStatus 0x40; Mac OS's interrupt select is s6). LOAD_QUAD's value goes into the command's cmdDep in memory (dbdma.cpp's `xfer_quad`; before 2026-10-08 it was kept inside only). Channels 2 and 3 reach MACE's registers with a quad through the system space (key 6) to Grand Central's window, a byte in a clock the CPU leaves Grand Central alone (2026-10-08: Mac OS's Ethernet driver ends each transmit with LOAD_QUADs of MACE's XMTRC, XMTFS and IR at F3011040, F3011030, F3011080, which so clear XMTSV and IR as the CPU's reads do). Left out there: such quads to any other device (they read 0 and write nothing), channels A, 8 and 9's quads outside RAM and the ROM (likewise), the keys other than 0 for data, the other device status bits. Channel 1 (the floppy's, 2026-10-08) is a `MacPPC7300_dbdma` too, SWIM3's sectors on its device side. Channel 0 (Curio's) stores its registers and reads them back (RUN and PAUSE follow writes; ACTIVE is never set): no external SCSI target ever moves data. Channels 4-7 (serial) read 0, as in dingusppc. | Each channel runs a program of descriptors from memory (dbdma.cpp). | The serial channels if Mac OS's serial driver uses DMA; 0 and 1 with an external disk or a floppy image. |
| VIA | Registers implemented; T1 and T2 count at 783,360 Hz and set their flags as dingusppc's do; the interrupt (IFR & IER) is Grand Central's source 12 (2026-10-07). Port B is a 6522's (the output register holds all eight bits; PB3 reads Cuda's TREQ, the other input pins 0); the shift register is clocked by Cuda on CB1 in the two modes Cuda's protocol uses (shift out under CB1, 111; shift in under CB1, 011), as MAME's 6522 does them: the flag at the eighth falling edge out, the eighth rising edge in. Port A, the CA1/CA2/CB1/CB2 flags and the other shift modes are not modelled (Mac OS enables only T2 and the shift register's interrupts, `vIER` A0 and 84). | A 6522 cell with Cuda on port B and the shift register, its interrupt Grand Central's source 12. | Anything that enables the CB1 or CA flags. |
| Cuda | The chip itself: see its own section below. | - | - |
| ESCC (serial) | `MacPPC7300_escc.sv` (2026-10-07): a Z85C30's asynchronous mode. Channel A, the modem port, is the MiSTer's UART (OSD: UART = Modem port), transmitting and receiving at the rate the baud-rate generator is set to (RTxC 3.6864 MHz; Open Firmware: 38,400 baud, 8 bits, 2 stop bits); RR0's receive and transmit-buffer bits, RR1's all-sent, a three-byte receive FIFO. Channel B has the same registers and no line. Interrupts (2026-10-08, the Z85C30's manual; dingusppc has none): receive (first character, every character, special condition: an overrun), transmit (the buffer emptied), external/status (never: no watched line changes), WR0's reset commands, WR9's master enable, RR3's pending bits, RR2 in channel B the vector with the status (WR9 bit 4 high or low); no interrupt is ever under service (no acknowledge cycle on this bus); channel A's on Grand Central's source 0F, B's on 10. The synchronous modes as far as LocalTalk with an empty printer port needs them (2026-10-08): sync/hunt reads 1 (no flag ever arrives: the line is free; dingusppc sets it since its commit ad9a9dbf, without which "the LocalTalk driver [waits] forever for the line to become ready for transmission", which is where Open Transport's AppleTalk start-up stopped on the board), bytes go out as their data bits at 230,400 bit/s (16 RTxC clocks; or the baud-rate generator), and an underrun after WR0's "reset Tx underrun/EOM latch" sends the CRC and closing flag (24 bits) and sets the latch with its external/status interrupt; RR1's all sent reads 1. Grand Central's LocalTalk helper (MacRISC registers 8-B: recovery count, Start A and B, Detect AB) as dingusppc's. Serial MIDI, PPP and the printer (2026-10-08, as the Quadra 800 core): WR11's TRxC clock source is a MIDI interface's 1 MHz, always there (x32: 31,250 bit/s; `run_escc` measures it, and 38,400, 57,600 and 115,200); the modem port's CTS is the MiSTer UART's (RR0 bit 5 uninverted: 0 clear to send, the Quadra's finding with an ImageWriter; its change an external/status interrupt), the UART's RTS asks the other end to wait while a received byte waits; the modem port's transmit also drives the MT32-pi's MIDI in, and in the Main's MIDI mode the user port's MIDI joins its receive. Left out: receiving in the synchronous modes, DMA (channels 4-7), the DPLL and the encodings (FM0, NRZI), the CRC's value, zero insertion, abort and break detection, DCD (0) and the printer port's CTS (0), WR5's RTS and DTR pins, the baud-rate generator's zero count, PCLK (taken to be RTxC), and the read registers dingusppc does not keep (RR0, RR1, RR2, RR3 and RR8 answer). One and a half stop bits are sent as two. Not tried on the board: MIDI, PPP, printing (the user and Discord testers). | Two Z85C30 channels (escc.cpp: transmits at once, RR0 always "empty", no interrupts). | LocalTalk with something on the printer port; DCD. |
| AWACS (sound) | `MacPPC7300_awacs.sv` (2026-10-08): the registers as dingusppc's (control, codec control, codec status 00314000: available, Crystal, Screamer; clip count, byte swap, frame count), except that control, clip count and frame count read back as they were written (2026-10-09: dingusppc and this file returned them byte-swapped, so Mac OS's read-modify-write of the control register, seen in the board's trace, set 44,100 Hz and then put the chime's 22,050 back: every Mac OS sound at half speed) and that a byte or halfword write changes only its bytes; the CPU's accesses to AWACS and DMA channel 8 are in the trace (kind 4); and the samples moving: 16-bit stereo frames from DMA channel 8 at the control register's rate (Screamer's table: 44,100 down to 7,350 Hz; the ROM's chime asks for 22,050) through an 8-byte FIFO to the MiSTer's audio outputs, the last frame held when the channel has not delivered one (2026-10-09: it was 0, a click), a part frame left in the FIFO by a stopped channel dropped (2026-10-09: it was kept, and every frame after the next start came byte-shifted: distorted sound until another stop happened to realign it); frames of silence into DMA channel 9 while it runs. The frame count counts the frames played while channel 8 is active (dingusppc's never counts). Left out: the codec's registers (attenuation, mute, gain, input select: stored, change nothing, as in dingusppc), its interrupt (11), the audio processor on Cuda's I2C (dingusppc: a TDA7433 at 45), a real input. Not measured: whether the 7300's codec reads the rate code as Screamer's table does (dingusppc and Linux's `awacs` driver agree; MAME's AWACS takes the word unswapped, which would play the chime at 44,100 Hz). | AWACS fed by DMA channels 8 and 9. | Volume and mute (Mac OS's Sound control panel), if they are not done in software. |
| NVRAM | 8 KB, implemented, through the address-high latch at 1D000 and the data window at 1F000. Zeros when the core is loaded, as dingusppc without a file, unless `games/MacPPC7300/boot1.rom` holds an image, which the core loads at its start (`syn/nvram_of_prompt.bin`: Open Firmware's own defaults with `auto-boot?` false; `verilator/nvram.py` makes and changes such images). A reset leaves it as it is. Kept on the SD card (milestone P, 2026-10-08, `MacPPC7300_nvsave.sv`, the Quadra 800 core's scheme): an 8 KB image on hps_io's block slot 2 (the OSD's "Mount NVRAM", a .nvr file; `syn\mister.py make-nvr` makes an empty one) is loaded when it mounts, the machine held in reset meanwhile, and the NVRAM is written back to it 2 s after the CPU's last write to it, or when the OSD opens. Without an image nothing is kept. | Battery-backed: keeps Open Firmware's settings. | - |
| Board register 1 | E13F, as dingusppc builds it for a 7600 (no composite video, fast SCSI present, factory tests off). | The same, from the board. | - |
| Ethernet address ROM | 08 00 07 44 55 66 00 00 (dingusppc's made-up address). | The machine's own address. | Networking. |
| Curio SCSI (53C94) | `MacPPC7300_sc53c94.sv` (milestone E): the Am53CF94 cell's registers, read and write maps apart, as dingusppc's `sc53c94.cpp`; the two-deep command FIFO; the 16-byte data FIFO; reset chip, reset bus (RST for 25 us; the interrupt unless configuration 1 disables it), clear FIFO, no operation, reset ATN, enable selection, and the three selections, which on the empty bus end in a disconnect interrupt after the selection timeout; the extended transfer count with ENF, the part ID (0C, dingusppc's) in it after a chip reset; the interrupt line, Grand Central's source 0C. Left out: targets, the information phases (transfer, command complete, message accepted, transfer pad: an invalid-command interrupt here, as on a 53C94 that is not connected; dingusppc stops), DMA and the pseudo-DMA port, reselection, the target-mode commands, parity, the phase latch (no target ever drives a phase), the synchronous period and offset (written, unused). | The external SCSI controller (sc53c94.cpp). | External SCSI devices. |
| Curio's selection timeout | 8192 x the clock conversion factor x the timeout register, in the chip's clocks (the 53C94's formula, as MAME's `ncr53c90.cpp`), the chip's clock 25 MHz (`SCSI_HZ`): the ROM's factor 5 and timeout A7 make 273.6 ms. | The clock is Apple's: Open Firmware's device tree gives `/bandit/gc/53c94` `clock-frequency` 017D7840, 25 MHz (and MESH 02FAF080, 50 MHz), read on the board 2026-10-07. dingusppc waits a fixed 250 ms. Whether the chip counts exactly the 53C94's formula is not measured. | `hwprobe/` (built 2026-10-07, waiting for a run on the 7300) times a selection of an empty ID at two timeout values. |
| MESH SCSI | `MacPPC7300_mesh.sv` (milestones E and S): the registers as dingusppc's `mesh.cpp` (the ID E2, the transfer count counting down, the 16-byte FIFO and its count, the sequence register, bus status 0 and 1 reading the bus and driving MESH's lines, exception, error 0, interrupt and mask, destination ID, synchronous parameters, the selection timeout); the bus at the signal level with the disks on it (`MacPPC7300_scsidisk`); arbitrate, select (done when a target answers with BSY), the information phases (command, status, data out and in, message out and in: a REQ/ACK handshake a byte, a REQ in another phase a phase-mismatch exception), bus free (ACK let go, also with ATN up, 2026-10-08: dingusppc keeps it and moves its target on by hand; done when BSY drops, a phase mismatch if the target asks for more), reselection on and off (no command done: see the next row), reset MESH, flush FIFO, parity on and off; DMA (the sequence's bit 7) for data out and in through DBDMA channel A; dingusppc's bus-controller timing (`scsibusctrl.cpp`: 1,200 ns until arbitration, 2,400 ns of it, won), and with no target a selection timeout after the register's value x 10 ms (the ROM writes 0x19: 250 ms, dingusppc's fixed `SEL_TIME_OUT`; the ROM computes it as milliseconds / 10, `nitt` 43 at FFEB7C1C); the interrupt line, Grand Central's source 0D, as any unmasked interrupt bit. As Linux's `mesh.c` uses the chip where dingusppc has no model: ACK stays up after a message in's last byte until the next command (dingusppc does the same), the data phases' count of 0 is 65,536. Our guess, not measured: ACK stays up after the status byte too, until the next command (the 7300's SIM waits after the status for REQ to drop, FFEB8D98, before it asks for the message; a target that asks at once, as BlueSCSI's can, would leave it waiting for ever unless MESH holds it off; with ACK released, the simulation hung there at 460 million instructions once an interrupt came between command done and that read). dingusppc shows the target in MESSAGE IN with neither REQ nor ACK at that point (bus status 07). Choices of ours: a DMA data in's command done waits until the FIFO and the DMA channel have emptied (Linux waits up to 50 us for the FIFO after it; Mac OS's driver does not wait); the bytes go at the CPU's clock's pace (about 7 clocks each: 9 MB/s, about a fast SCSI bus's), whatever the synchronous parameters say. Left out: reselection, target mode, parity, the error register's conditions (an unexpected disconnect, a reset). The exception register is cleared as dingusppc clears it (arbitrate keeps only arbitration lost, select only selection timeout); arbitration is never lost (MESH is the only initiator). | The internal SCSI controller, our boot disk path (mesh.cpp). dingusppc's MESH has no DMA out: Mac OS 7.6.1 hangs there in dingusppc at its first write (the volume's master directory block, 464 million instructions). | Reselection, if a target ever disconnects (ours never do). |

## Things the ROM measures that a slower machine changes

- The bus clock: VIA timer 1 measured against the decrementer, so the
  decrementer must run at bus clock / 4 (12.5 MHz, `TB_HZ`) against the VIA's
  783,360 Hz. Both are made exactly by phase accumulation in `MacPPC7300_machine`.
- The CPU clock: a decrementer-timed loop of eight dependent `addi` and a
  `bdnz`, assuming one instruction a clock. This core, slower per clock than
  a 604, will report a lower CPU clock to Open Firmware and Mac OS. That is a
  true reading of its speed, not a stub; noted so that it does not surprise.
  (Both from `rom7600/README.md`.)

## Not on the bus at all yet

- The modem port's RTS and DTR as software sets them (WR5): the UART's RTS
  is "a received byte waits", its DTR the other end's own DSR (2026-10-08,
  as the Quadra 800 core); the printer port has no line.
- Sound input (AWACS records silence).
- A network unless the OSD's Ethernet is on (MACE's cable is unplugged then).
- Writing to a floppy disk (SWIM3 reads images only; every disk shows as
  locked).

## The lockstep bench's accommodations (`verilator/core_main.cpp`, machine mode)

Not stubs in the machine, but places where the comparison with dingusppc
takes the core's word for something, so a fault there would not show up as a
lockstep mismatch:

- A device read in the reference returns the value the core's machine
  returned (the reference has no devices of its own). The reads are checked
  to happen in the same order, at the same address and size; writes are
  checked for address, size and data.
- `mftb`, `mfspr` of the time base and `mfdec` give the core's value.
- The decrementer and external interrupts are taken in the reference where
  the core took them.
- `mtspr` and `mfspr` of an SPR the real 604 does not have (the README's
  list): the core takes the program exception (illegal) as the chip does;
  dingusppc accepts the 604e's MMCR1, PMC3 and PMC4, which the NanoKernel
  probes (FFF131B0 on), so the reference is made to take the exception
  with the core's SRR0, SRR1 and MSR.
- MSR[PM] (bit 29, which the 604 keeps: measured) through `rfi` and
  exception entry: a 604 copies SRR1's low 16 bits into MSR on `rfi` and
  MSR's into SRR1 on an exception, PM among them; dingusppc leaves PM out
  of both (`ppc_rfi` replaces 0x87C0FF73, `ppc_exception_handler` keeps
  0x0000FF73). The NanoKernel returns to Mac OS with PM set (FFF12C50,
  33.2 million instructions) and Mac OS traps with it set, so the
  reference's MSR takes PM from SRR1 after every `rfi`, and its SRR1 takes
  PM from the MSR at every exception and injected interrupt. Not
  machine-mode only: the 604's rule holds in the CPU suite too.
- A DSI at `dcbst`, `dcbf`, `icbi` or `dcbi`: the core translates them as
  loads (`dcbi` as a store), as the architecture and the 604 do; dingusppc
  does not translate them at all. The NanoKernel fills the hardware page
  table on demand, so when Open Firmware's flush word, called from Mac OS,
  runs `dcbst` over code it has just compiled (FF808D14, 33.2 million
  instructions, DAR FF840940, DSISR 40000000), the real machine takes the
  same DSI and the NanoKernel installs the PTE and retries. The reference
  is made to take it (SRR0, SRR1, DAR from its own state; DSISR "no
  translation", or the protection bit when dingusppc's MMU does translate
  the address, which the handler's read of DSISR then checks).
- Cuda's clock runs 15 times fast while it holds the CPU in reset
  (`CUDA_FAST_BOOT`, the machine bench's build only), so the cold start
  takes 5.4 million cycles, not 83 million. Cuda's instructions are the
  same; only its clock (and so its real-time clock) is ahead.
- The page table's R and C bits are the core's (2026-10-07): a 604 sets R
  in the PTE when it loads it and C at the first store through it;
  dingusppc's MMU does not always. When a word loaded from memory differs
  only in those two bits (the NanoKernel reads PTEs for Virtual Memory's
  page replacement, FFF14F6C, from 466.76 million instructions of the
  7.6.1 disk boot), the reference takes the core's word, into its register
  and its RAM. With Virtual Memory on, that is the only lockstep difference
  up to the bus error at 497.8 million.

And Cuda's own bench (`verilator/cuda_main.cpp`, `run_cuda.py`): MAME's
6805 core is handed the values the RTL read from the registers (0000-001F)
and takes interrupts where the RTL took them; the VIA and the host there
are models (MAME's 6522 shift register, Linux's via-cuda.c protocol paced
as the 7600's ROM paces it), not the 7600's RTL or ROM.
