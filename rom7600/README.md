# Power Macintosh 7600 ROM, annotated disassembly

The 4 MB boot ROM of the user's own Power Macintosh 7600 (`ppctest/runs/my7600.rom`;
68k header machine 07, version 7D, release 28F2, the "TNT" universal ROM; Open
Firmware 1.0.5), taken apart region by region: what each part is, how we know, a
listing of every part at the address it runs at, Open Firmware's dictionary and
detokenized FCode, and the hardware the ROM touches. Byte 0 of the file is physical
FFC00000; everything is big-endian. Physical address = ROM offset + FFC00000.

Everything here is generated by the scripts in `tools/` (see "Regenerating") except
this README and the hand-written notes in `tools/annotations.py`. The directory is
committed (since 2026-10-08, at the user's request); the ROM image itself is not.

## ROM layout

| ROM offset | physical | size | what | how we know |
|---|---|---|---|---|
| 000000-0D34FF | FFC00000 | 0D3500 | 68k ROM header and code (the Toolbox/OS "universal ROM" code) | 68k header (checksum 9630C68B, reset PC +2A, RomSize 300000); executed by the 68k emulator in the coverage run (32,856 distinct 68k instructions) |
| 0D3500-0D4CFF | FFCD3500 | 001800 | trap dispatch tables: Toolbox A800-ABFF, OS A000-A0FF, OS again | header DispTableOff; the RAM trap tables ($E00, $400) after boot equal entry+FFC00000 |
| 0D4D00-2F35CA | FFCD4D00 | 21E8CB | ROM resources: 180 (30 PEF code fragments, 62 68k code, 88 data); list entries interleaved with the data | header RomRsrc = 0D4D00; each data block has a 16-byte header tagged "Kurt" |
| 2F35CB-2FFED3 | FFEF35CB | 00C909 | fill (`kc` pattern) | content |
| 2FFED4-2FFFFF | FFEFFED4 | 00012C | slot-0 declaration ROM ("Macintosh CPU Family 6.0", "Macintosh 4A") | NuBus-style format block at the top: test pattern 5A932BC7, byte lanes 0F |

| 30E000-30FFFF | FFF0E000 | 002000 | zero | |

| 320000-32FFFF | FFF20000 | 010000 | HWInit: ROM diagnostics, Serial Test Manager (code to 321FFF) | ConfigInfo HWInitCodeOffset/Size; called at FFF2003C; source path string `...BootPowerPC.src:Diagnostics:...Diagnostics.s` |
| 330000-34FFFF | FFF30000 | 020000 | Open Firmware 1.0.5 bundle: an XCOFF file (to 34885B) | ConfigInfo OpenFWBundleOffset/Size, LA_OpenFirmware FF800000, PA_OpenFirmware 00400000; XCOFF magic 01DF; called at FFF3003C |
| 350000-35FFFF | FFF50000 | 010000 | zero | |
| 360000-37FFFF | FFF60000 | 020000 | the 68k emulator (code to 3773FF) | ConfigInfo EmulatorCodeOffset/Size, LA_EmulatorCode 68060000; runs mapped at 68060000 in user mode |
| 380000-3FFFFF | FFF80000 | 080000 | the emulator's opcode dispatch table: 8 bytes (two PowerPC instructions) per 68k opcode word | ConfigInfo OpcodeTableOffset/Size, LA_DispatchTable 68080000 |

Inside the Open Firmware bundle (offsets in ROM): 330000 XCOFF file header and one
section header (".text", 18820 bytes at file offset 3C; the timestamp field reads
"Gary"); 33003C the text, starting with Open Firmware's own header (the sizes of its
parts); 33003C-3367E3 the native Forth kernel, PowerPC code with 501 dictionary
headers, 235 of them with names (this part is copied to physical 00408000 and runs at
FF808000); 3367E4-3459BD
the main FCode image (version1 header, length F1DA) that builds the system at
startup; 3459BE-34885B nine more FCode images in a linked directory, loaded with
`byte-load-file` for Bandit (106B:0001), Chaos (106B:0003, class 060000), Control
(106B:0003, class 038000), PlanB (106B:0004), MESH, the serial channel driver (loaded
for both SCC channels), SCSI disk ("sd"), SCSI tape ("st") and a PCI-PCI bridge
(class 060400).

The 30 PEF containers (`ncod`, `nlib`, `ndrv`, `nitt` resources) are the native
parts of the Mac OS ROM: CodeFragmentMgr, MixedMode, InterfaceLib,
PrivateInterfaceLib, MathLib, StdCLib, NQD (native QuickDraw), FontDispatch, the
Memory Manager, NameRegistryLib, DriverServicesLib, PCILib, InterruptTreeTNT,
MotherBoardHAL, the native SCSI Manager 4.3 (`nitt` 43 "Native 4.3"), NativeNub, the
video and other drivers (`ndrv` 99, 100, 101, 505) and more; see `resources/resources.txt`.

## How the ROM runs (from the coverage run)

1. Reset: FFF00100, MSR 00000040. The start-up code at FFF03000 identifies the CPU,
   maps I/O with a BAT, configures Bandit and Grand Central, talks to Cuda, starts the
   boot chime, sets up and sizes memory, runs HWInit (FFF2003C), measures the clocks.
   Instruction 0 to about 1.44 million.
2. Open Firmware (called at FFF3003C, instruction 1,436,733): starts in ROM, builds its
   page table at physical 004E0000, copies its kernel to 00408000 and runs translated at
   FF80xxxx (MSR 00003070) from instruction 1.5 million. It interprets the FCode images
   (device tree, NVRAM, drivers), probes PCI, and "boots" the Mac OS by returning to the
   start-up code (instruction 27.95 million).
3. The start-up code jumps to the NanoKernel (FFF10000, instruction 27,955,010), which
   maps the emulator and opcode table at 68060000/68080000 and starts the 68k emulator in
   user mode (MSR 0000D072, instruction 28,358,933) at the 68k ROM's reset entry.
4. The Mac OS ROM boots: 68k code under emulation, native PEF code executed in place in
   ROM (FFDxxxxx) or copied to RAM (`ndrv` 100 and 505), SCSI and floppy probing, video
   set-up. From instruction 32 million it calls back into Open Firmware's client
   interface (Open Firmware code at FF80xxxx runs in user mode; the 68k ROM holds the
   service names "finddevice", "getprop", "nextprop", "peer" around FFC566F6-FFC57898)
   apparently to copy the device tree into the Name Registry (strings such as
   "driver,AAPL,MacOS,PowerPC" and "ExpertEntryPoint" sit next to them), so Open
   Firmware's RAM (physical 00400000-004FFFFF) must survive the hand-over. With no
   disk attached the Mac OS ends up in the start-up device search loop at FFC0218A
   (retry every 15 ticks), where the run stops at instruction 10^9.

## Method

* **Layout** from the structures themselves: the 68k ROM header (offsets of the trap
  tables and the resource list, ROM size), the resource list (walked from the header),
  the ConfigInfo record (found by its "Boot TNT" string at 30D000, every offset field
  resolved), the XCOFF header of the Open Firmware bundle, the PEF headers of the
  native fragments, the declaration ROM's format block. Gaps were checked for content
  (zero or fill).
* **Execution evidence** from `tools/romcov`: a copy of the existing headless
  dingusppc 7600 harness (`verilator/machref`) that steps the machine one instruction
  at a time and records, for each instruction, the physical word it was fetched from
  (first instruction count and effective address), every (effective page, physical
  page, MSR) pair, RAM dumps at chosen points, the device log, and the 68k emulator's
  PC at every opcode dispatch. Run: 10^9 instructions, 32 MB, 604 (PVR 00040303),
  deterministic, about 30 s. RAM code that is a byte-for-byte copy of ROM code (the
  Open Firmware kernel, two `ndrv` drivers) is mapped back to the ROM.
* **68k PC**: in the emulator, r24 always points 2 bytes past the opcode being
  dispatched (`lhau r27,2(r24)` prefetches; each table entry starts with r24 = opcode+2,
  r27 = the word after the opcode), so r24-2 at the first instruction of every opcode
  table entry is the executed 68k instruction (verified against a trace).
* **PowerPC listings**: dingusppc's disassembler (`cpu/ppc/ppcdisasm.cpp`, unmodified,
  behind `tools/ppcdis_dingus.cpp`), then in Python (`tools/ppclist.py`): code vs data
  (invalid encodings, ASCII runs, "bl over a table" constructs where the callee reads
  through the return address, ROM addresses in unreached words, explicit data ranges),
  reachability from executed words and known entries, labels at branch targets
  (`sub_` for calls, `loc_` otherwise, names where known), SPR names (601/603/604),
  and a constant tracker within basic blocks (lis/addi/ori/addis/mr) that names
  addresses of the 7600 I/O map when they are formed and when loads/stores use them.
* **68k listings**: MAME's 68k disassembler (68040 mode; `tools/mamedis.cpp`) as a
  server, recursive descent (`tools/m68klist.py`) from the header vectors, every trap
  implementation of the dispatch tables (labelled `_TrapName`), driver header entries
  and every executed 68k instruction; the remaining gaps are decoded linearly and kept
  as code (flag `?`) only when they form plausible runs ending in a branch/return,
  else shown as data. A-line traps by name; low-memory globals by name. Trap and
  low-memory names come from two local, independent tables (MAME's
  `src/mame/apple/mactoolbox.cpp`, 855 traps with Snow's `consts.rs`; 322 low-memory
  globals from Snow); they agree except for four aliases.
* **PEF**: `tools/pef.py` parses sections, the loader (imports, exports, entry points),
  runs the relocation bytecode and unpacks pattern-initialized data; exported
  functions are labelled through their transition vectors, TOC loads (`lwz rX,d(r2)`)
  are named, cross-TOC glue becomes `glue_<import>`.
* **Open Firmware**: the dictionary header format was found by inspection (see
  `tools/ofw.py`); headers in the ROM kernel and in the RAM dump at instruction
  27,400,000 (Open Firmware complete) were walked and grouped by wordlist; the FCode
  token table was found at physical 00404000 (FF804000; xt per token, bit 0 =
  immediate). The FCode images were detokenized with the IEEE 1275 token table, the
  kernel's own header names, and the names the images define, plus three Apple
  extensions identified from their use: token 401 (start of locals, one inline count
  byte), 410-417 (fetch local n), 418-41F (store local n). Token numbers after
  new-token/named-token/external-token are encoded like tokens (1 or 2 bytes), not as
  the 16-bit field of IEEE 1275. The whole main image (F1DA bytes) and the nine
  others decode to their end markers without losing sync.
* **Cross-check** (`crosscheck.txt`): 169,513 PowerPC words from nine regions through
  dingusppc and MAME's PowerPC disassembler: after normalising notation (extended
  mnemonics, shifted immediates, rotate masks, CR-bit names, BO/BI spelling) only
  86 words differ in validity: 57 that MAME decodes and dingusppc rejects (update forms
  with rA=0, which are invalid, and words in data) and 29 the other way round (POWER
  instructions of the 601 that MAME's PowerPC mode lacks, and words in data). The
  cross-check found three dingusppc problems that the listings correct: 603 `tlbld`/
  `tlbli` with rS=rA=0 rejected (the 603 TLB-miss vectors at FFF01000-FFF012FF use
  them), `lfsu`/`lfdu` rejected when rA equals the FPR number, and some reserved
  encodings accepted (sc with reserved bits, 64-bit compares, Rc=1 on mfspr/mtspr,
  an empty text for some opcode-19 words); and that dingusppc prints AltiVec opcode-4
  words as a message on stdout (the wrapper prints them as data). 68k: all 254,202
  instruction starts of the main 68k listing through MAME and binutils (QEMU's
  `disas/m68k.c`, compiled unmodified): same length and mnemonic for 96.7%, A-line
  traps (raw in both) 2.7%, same length with alias mnemonics 0.6% (`dbra`/`dbf`,
  `fmovem.l`/`fmovel`, one MAME error: 68030 PFLUSHA F000 2400 shown as "pflushr", fixed
  in the listing), 29 words binutils rejects (68030 MMU instructions such as `pmove
  tt0`, which MAME's 68040 mode accepts and the universal ROM contains, and data in
  `?` runs), 10 with different lengths, all in `?` runs that are really ASCII data.

## Listing format

PowerPC (`.lst` under `ppc/`, `of/`, PEF resources):

    FFF03104* 3C60F800  lis     r3, 0xF800                    ; = F8000000 Hammerhead registers

address, a flag, the raw word, the instruction, `;` comments. 68k (`68k/`, 68k
resources): address, flag, the instruction's bytes, the instruction. Flags:
`*` executed in the coverage run, blank = reached by control flow from executed code
or a known entry point, `?` = decodes as code but neither executed nor reached (dead
code, code reached only through tables, or data that decodes), `d` = shown as data
(`.long`, `.ascii`, `dc.b`, hex rows, `.space` for zero runs). Labels stand on their
own line before the address. Block comments from `tools/annotations.py` precede the
code they describe. Comments name hardware registers (`R GC_VIA.vIFR F3017A00 (1)` =
1-byte read), targets in other regions (`-> NanoKernel`), TOC entries, traps, low
memory.

## Regenerating

In WSL (gcc 13, make, python3; no packages needed), from this directory:

    bash tools/regen.sh                 # build tools, coverage run, all outputs
    SKIP_COV=1 bash tools/regen.sh      # reuse ~/.cache/macppc7300/romdisasm/cov

From Windows: `wsl --cd C:\Temp\mistercore\PPC_Mac\rom7600\tools -- bash ./regen.sh`.
`regen.sh` runs `build.sh` (make -j4: the three disassembler wrappers and `romcov`,
which compiles dingusppc headless into `~/.cache/macppc7300/romdisasm/build`; the
dingusppc, MAME and QEMU trees are only read), `run_cov.sh` (the coverage run into
`~/.cache/macppc7300/romdisasm/cov`, about 30 s, RAM dumps of 32 MB each),
`romdis.py` (all listings, about a minute), `hwsummary.py` and `crosscheck.py`. Paths
of the source trees are options of `romdis.py` (`--mame`, `--snow`) and variables of
the Makefile (`DINGUS`, `MAME`, `QEMU`). Temporary files go to
`~/.cache/macppc7300/romdisasm/tmp`.

## Notes for an emulator or FPGA implementation

Addresses are physical unless noted; "boot" = `ppc/ppc_boot_FFF00000.lst`.

**Reset and CPU set-up**

* The reset vector (FFF00100) decides between a cold start and a soft reset by
  SRR1[RI] and then HID0[NHR] (bit 15 on 603/604): either clear = hard reset ->
  FFF03000. A soft reset dispatches through a table SPRG3 points to. At power-on the
  core must present SRR1[RI]=0 (or HID0[NHR]=0).
* PVR>>16 selects the set-up: 1 (601), 3/6/7 (603 family), 4 (604) and anything else
  (treated like the 604: HID0 = 8000CC84, MMCR0/PMC1/PMC2/SDA cleared). The 601 paths
  use RTC registers, SR15 = 87F0000F (direct-store) instead of a BAT, and different
  instruction orders in the vectors. 603 software TLB-miss vectors are at
  FFF01000-FFF012FF.
* Before the first I/O access the start-up code clears all BATs, maps
  F0000000-FFFFFFFF with DBAT0 (F0001FFF / F0000032: 256 MB, WIMG 0110, read/write)
  and sets MSR[DR]; instruction fetch stays untranslated until Open Firmware.

**Hammerhead (F8000000)**

* CPU_ID is read as a 32-bit word: the top half is compared with 3001 (another memory
  controller, sets r21 = 1 and alternative code paths); the 7600 path needs anything
  else (dingusppc gives 0x39 in the top byte).
* The 68k ROM identifies the board again at FFC14844: byte F8000000 == 39 (TNT), then
  MOTHERBOARD_ID (long at F8000020) bit 0x40000000 set -> 3020, else Grand Central
  board register 1 (long at F301A000) bit 0x00080000 set -> 3022, else 3021 (the path
  taken in the coverage run, where dingusppc's board register reads 3FE10000); a
  top half of 3001 is the other memory controller again. Which model each value
  stands for is not established here, but the two bits must match the real board.
* WHO_AM_I (F80000B0) bit 0x08000000 set = secondary CPU, which parks in a doze loop
  waiting for an interrupt and then jumps to an address read from F2800000.
* CPU_SPEED (F8000030) bus-speed bits index the memory timing table (MEM_TIMING_0/1,
  REFRESH, ROM_TIMING at FFF03ED4, 4 entries of 32 bytes); MOTHERBOARD_ID (F8000020)
  bit 0x10 (burst ROM) selects the ROM timing; ARBITER_CONFIG is read and written
  back; L2 register (F80000E0) bit 7 starts an L2 flush/enable sequence via F80000F0.
* All 26 bank base register pairs (F80001C0-F80004F0, MSB at 1C0+20n, LSB at 1D0+20n)
  are first set to distinct 64 MB slots, each bank is sized, then programmed with its
  real base (banks packed from 0, 4 MB units), equal neighbouring banks get an
  interleave bit.

**RAM sizing (FFF0412C)** with data translation off, per bank, 1 MB steps up to
64 MB: "Kurt"/"Lika" (4B757274/4C697A61) in the last 8 bytes of every MB from the top
down, `dcbf` + `sync`, then a store of FFFFFFF0 to address FFFFFFF0 (ROM space) with
`dcbf` + `sync` to drive other data onto the bus, then read back; the first MB that
reads back is the top, mirroring from the base gives the size. Stores to ROM must be
ignored (no machine check), and a missing bank must not return the last value written.
The resulting bank table is written to NVRAM (total at 1044, base/size pairs at
1048+8n/104C+8n) and read back from there by later code.

**Bandit and Grand Central**

* The first Grand Central access follows PCI configuration through Bandit
  (CONFIG_ADDR F2800000 / CONFIG_DATA F2C00000, little-endian, `stwbrx`/`lwbrx`):
  Bandit itself is IDSEL AD11 (address 0000080C: register 0C <- 00FF0000), Grand
  Central IDSEL AD16 (00010010: BAR0 <- F3000000; 00010004: command <- 0016). Every
  address write is read back. Then GC_INT_MASK (F3000024) <- 80000000. (Values are
  the little-endian register values; the code writes them with `stwbrx`.) Open Firmware
  later probes Bandit, Chaos (F0800000/F0C00000) and the PCI devices again and
  assigns BARs (Control's registers at 94000000 and VRAM at 90000000 in this run).
* NVRAM (8 KB) through Grand Central: page = address >> 5 written to F301D000 with
  `stwbrx` (the page lands in the register's first byte), then byte (address & 1F) at
  F301F000 + 16*(address & 1F). Open Firmware writes the page register with byte
  stores. Mac OS parameter RAM (XPRAM) is NVRAM 1300-13FF: the boot code reads XPRAM
  byte 8 for the chime volume. HWInit writes LR (1250), CTR (1270) and r0-r31
  (11D0+4n) into NVRAM on every boot.
* Grand Central interrupt numbers as Open Firmware publishes them (`aapl,interrupts`,
  `of/of_fcode.txt`): 53C94 SCSI 0C (DMA 0), MESH 0D (DMA 0A), MACE 0E (DMA 2, 3),
  SCC channel A 0F (DMA 4, 5), channel B 10 (DMA 6, 7), AWACS 11 (DMA 8, 9), VIA/Cuda
  12, SWIM3 13 (DMA 1), sixty6 1B, Platinum 1E. In the run the NanoKernel reads
  GC_INT_LEVELS (F300002C) and GC_INT_MASK and writes GC_INT_CLEAR (F3000028) about
  10,900 times each; GC_INT_EVENTS (F3000020) is never read. ConfigInfo gives
  LA_InterruptCtl F3000000 and the masks 00200000 / FF9FFFFF / 00E00000.
* Device registers used, with counts and values: `hw_access.txt`. The device space
  blocks: Curio 10000, MACE 11000, SCC 12000 (compatible addressing, used by the 68k
  side) and 13000 (MacRISC addressing, used by Open Firmware), AWACS 14000, SWIM3
  15000, VIA 16000 (registers 0x200 apart), MESH 18000, Ethernet address ROM 19000
  (read by Open Firmware: 08 00 07 44 55 66 in dingusppc), board register 1A000,
  RaDACal 1B000 (CLUT, written by the video driver), sixty6 1C000 (probed), NVRAM
  1D000/1F000.

**Boot chime and DBDMA** The chime is the ROM resource `beep` 0 at FFE00010. Its
header word 10 is checked, the rate goes to the AWACS control register (F3014000),
the volume through the AWACS codec control register (F3014010, waiting on its busy
bit 0x01000000), then the audio-out DBDMA channel gets cmdptr = FFE00020 (a command
list inside the resource, little-endian OUTPUT_MORE descriptors pointing at sample
data in ROM from FFE000A0) and control = RUN. DBDMA must read descriptors and data
from ROM. The error beep is `beep` 1 (FFE40010).

**Cuda (VIA at F3016000)** VIA init: vBufA 10, vDirA 58, vBufB 38, vDirB 30 (PB5 TIP
and PB4 BYTEACK out, PB3 TREQ in), vPCR 0, vACR 1C, vIER 7F, then vACR &= EF and vIER 84.
The synchronisation (FFF047C0) toggles TIP/BYTEACK and waits on TREQ and the shift
register flag (vIFR bit 2) with loop timeouts of D05 and 3A98 iterations of VIA reads.
Then a pseudo packet, command 22 (I2C read/write), data 88 61 55 (a write to I2C
address 88). Everything later (Open Firmware, the 68k ADB/Cuda code) uses the same
handshake; vIFR is read about 136,000 times in the run (115,000 of them by 68k code),
and the Mac OS uses VIA timer 2 heavily.

**Clocks** The bus clock is measured by starting VIA timer 1 at FFFF and running the
decrementer down from 3FFFF, then looking up the elapsed VIA ticks in a table (33,
40, 50 MHz...); the CPU clock by timing 1024 iterations of 8 dependent `addi` + `bdnz`
with the decrementer and assuming 1 instruction per cycle, rounded to a table entry
within 1/512. So the decrementer/timebase must run at bus/4 against the VIA's
783.36 kHz, and a core that does not sustain 1 IPC on that loop reports a lower CPU
clock to Open Firmware and the OS. The results go to the info area handed to Open
Firmware (CPU, bus and timebase Hz).

**Open Firmware** is called with r3/r4 = info areas, r5 = 00400000; it sets SDR1 =
004E0000 (64 KB page table at 004E0000), runs at FF800000-FF8FFFFF (= 00400000), uses
physical 00400000-004FFFFF, and returns to the start-up code with r5 = its result
(stored at 00400000, passed to the NanoKernel in r7). Its Forth is native
subroutine-threaded PowerPC: r20 = top of the data stack, r31 = data stack pointer,
r19 = top of the return stack, r30 = return stack pointer; colon definitions start
`stwu r19,-4(r30); mflr r19` and end `b exit`. The device tree it builds (bandit, gc
and its children, chaos/control, hammerhead...) is in `of/of_fcode.txt` with `reg`
and interrupt values.

**NanoKernel and the 68k emulator** The NanoKernel runs untranslated at FFF10000
(MSR 00001040/00001050). The emulator runs in user mode (MSR 0000D072) at effective
68060000 (= FFF60000) with its opcode table at 68080000 (= FFF80000): every 68k
instruction executes one table entry (two instructions) and a handler, all fetched
from ROM, so instruction fetch from ROM (cached, mapped through the page table) is on
the emulator's hot path; the table alone is 512 KB. 68k registers: D0-D7 = r8-r15,
A0-A6 = r16-r22, A7 = r1, PC = r24 (+2), prefetched word r27, dispatch address r29,
emulator code base r30, emulator data r31 (68FFF000). The 68k ROM runs at its
physical address (ROMBase = FFC00000, not 40800000 as on NuBus Power Macs). PEF code
runs in place from ROM at FFDxxxxx in user mode.

**Surprises** HWInit rewrites part of the NVRAM on every boot; the RAM bank table is
kept in NVRAM; the boot chime is played by DBDMA straight out of ROM; RAM sizing stores
to ROM space; a `CPU_ID == 3001` check selects code for a different memory controller
(this ROM serves several machines; Open Firmware also knows the 7200's Platinum video
and a second Bandit at F4000000); the Open Firmware XCOFF timestamp field reads
"Gary".

## What is not done

* 68k code reached only through computed jumps or tables is not distinguished from
  data that decodes as instructions: such bytes carry the `?` flag (about 157,000 of
  the 254,000 instructions of the main 68k region; the trap tables and the coverage run
  reach 97,000). The same holds, at a smaller scale, for the PowerPC regions and the
  68k code resources.
* Routines have no names beyond trap implementations, MacsBug names in the ROM (shown
  as comments), PEF exports/imports, Forth words, exception vectors and a few
  hand-written notes; NanoKernel and emulator internals are labelled by address only
  (emulator handlers by the first opcode that uses them).
* The coverage run covers one path: one machine configuration (dingusppc 7600, 32 MB,
  604), no disk, no keyboard input, no NVRAM file. Code for other CPUs, machines,
  error paths, the Serial Test Manager and most of the Toolbox did not run.
* The ConfigInfo page-map and BAT tables are decoded with an inferred meaning of
  bit 0x200 (offset relative to the record); the 68k ROM header fields after
  InitSys7ToolboxOff are shown raw.
* The Open Firmware device tree is not dumped from RAM (its structure is not
  decoded); the FCode that builds it is.
