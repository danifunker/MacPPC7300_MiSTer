## Where things stand (2026-10-06, evening)

- **M0-M5 done**, all committed on `main`, nothing pushed. `rtl\DSPPC604\` is the CPU: a six-stage pipeline (`DSPPC604.sv`), the integer units, the FPU, the MMU (BATs, segment registers, hardware page-table walk, two TLBs), two 16 KB four-way caches with a snoop port, `DSPPC604_memcdc` carrying the memory port into another clock. The FPU operand register is on (`FPU_OPERAND_REG = 1`, 2 % of floating-point cycles).
- **The CPU's bus, which is the only bus designed so far.** The memory port: one request at a time, `mem_req` held until `mem_ack`, either a 32-byte line (`mem_line`: the cache fills and write-backs; word 0, the lowest address, in bits 255-224) or one word with four byte enables (`mem_be`; the byte at the lowest address is `mem_be[3]` and bits 31-24), address `mem_addr[31:2]`, `mem_we`, `mem_wdata`/`mem_rdata[255:0]`. Data requests go before instruction fetches inside the CPU. A word request is a cache-inhibited access (the BATs' or the page's I bit; with translation off the 604 treats everything as cacheable, so the ROM reaches device registers through BATs with I set), or any access with the cache off. The snoop port: anything else that touches memory presents the line first (`snoop_req`, `snoop_we`, `snoop_addr[31:5]`) and proceeds after `snoop_ack`; that is the whole coherence protocol. Sideband inputs: `ext_irq` (level), `tb_tick` (one clock: advance the time base and decrementer), `reset_pc`. `DSPPC604_memcdc` carries the port into the memory clock: its `a_*` side is the CPU's port, its `b_*` side the same protocol in `clk_b` (`b_req`, `b_we`, `b_line`, `b_addr[31:2]`, `b_be`, `b_wdata`, `b_ack`, `b_rdata`), about two cycles of each clock each way, verified at 66 against 100, 130, 66 and 50 MHz by `verilator\cdc_main.cpp`.
- **Tests**: `python verilator\run_core.py` (54 runs) and `python verilator\run.py` (`--csv ppctest\runs\results_604_7300_of_run1.csv` for the 7300's vectors). Cycle counts to hold: 1.85 and 3.53 cycles per instruction on the 7600 golden programs, 1.87 and 3.81 on the 7300's, 2.5-3.0 on the plain lockstep programs, 2.9-3.4 translated. The bench is `verilator\core_main.cpp` (`--prog`, `--lockstep`, `--trace`, `--stall`, `--seed`, `--max-cycles`, `--show`, `--irq-every`, `--tb-run`); it serves the memory port from a software memory with random wait states. `verilator\progs.py` generates programs as instruction words (there is no cross compiler). The CPU has a retirement trace port (one pulse per operation: pc, instruction, the register written and its value, CR, XER, LR, CTR, FPSCR, MSR) and a trace of every data access as it reaches the cache.
- **The ROMs**: `ppctest\runs\my7600.rom` (4 MB, version `077D.28F2`, Open Firmware 1.0.5) and `my7300.rom` (checksum `5B38E8BD`), big-endian bytes as dumped, byte 0 at `FFC00000`. Reset: MSR `00000040` (IP set), first fetch at `FFF00100`. What the ROM leaves at the Open Firmware prompt (7300 run): HID0 `8000C084`, segment registers 0-15 holding VSIDs 0-15, SDR1 `0FFE0000`, the decrementer and time base running, a decrementer interrupt pending. A read of RAM space beyond the installed memory returns 0 with no exception (measured); there is no machine check.
- **The MiSTer side today**: `PPCMac.sv` is the template's `emu` module (ports in `sys\emu_ports.vh`): SDRAM pins tristated, UART tied off, a test pattern on the video output from the demo logic in `rtl\` (`cos.sv`, `lfsr.v`, `mycore.v`; the `pll` there is a Quartus PLL, 50 MHz in). `sys\` is the framework, never edited: `hps_io.sv` gives `status[127:0]` from the OSD options in `CONF_STR`, and file uploads through `ioctl_download`, `ioctl_index`, `ioctl_wr`, `ioctl_addr[26:0]`, `ioctl_dout[7:0]` (a byte per strobe, addresses counting up) and `ioctl_wait`; it has `uart_mode`/`uart_speed` from the Main menu. The framework has no SDRAM controller: cores bring their own, and the MiSTer cores' `sdram.sv` modules (GPL) are proven on these modules (16-bit data, `SDRAM_A[12:0]`, `SDRAM_BA[1:0]`, `SDRAM_DQML/DQMH`, the usual control lines). The DE10-Nano here carries a 64 MB or 128 MB module.

## The design of the machine's side, decided (build it this way; the open points are marked)

- **Where the machine sits.** `rtl\machine\PPCMac_machine.sv`, on the CPU's side of the clock crossing, in the CPU's clock: it takes the CPU's memory port, decodes the address, serves device accesses itself, and passes RAM and ROM accesses on to `DSPPC604_memcdc` and from there to the SDRAM controller. So the same memory port protocol runs through all of it, and every device runs at the CPU clock. The machine module also makes `ext_irq` and `tb_tick` for the CPU and takes the installed RAM size from the OSD. Nothing of the machine goes into `rtl\DSPPC604\`.
- **The map, first machine (7600, dingusppc's TNT).** RAM from 0, the installed size an OSD option; the ROM's 4 MB at `FFC00000` (`add_rom_region(0xFFC00000, 0x400000)` in `machinetnt.cpp`); the memory controller's registers at `F8000000`; Grand Central and its IOBus devices at `F3000000` and up (the lines in `machinetnt.cpp` name them: `F301A000`, `F301E000`, ...); the PCI bridge at `F2000000`. Take the whole table from `machinetnt.cpp` and the device headers it uses, and write it into the machine module as one table with the file and line cited for each entry. What is not in the table reads as zeros and ignores writes; writes to the ROM are ignored; nothing ever withholds an acknowledge (a device that is not there answers at once). Each device stub answers what dingusppc's device answers at reset, no more, until the ROM's progress asks for more.
- **Where the ROM lives.** In the top 4 MB of the SDRAM module, written there by the OSD upload before the CPU runs; the machine maps `FFC00000-FFFFFFFF` to SDRAM offset `module size - 4 MB`. RAM maps to SDRAM offset 0 and the installed size may not reach the ROM: 6 to 60 MB on a 64 MB module, 6 to 124 MB on a 128 MB one. **Mine to decide**: the 128 MB RAM option needs the ROM elsewhere (the HPS's DDR3 through the framework's `DDRAM_*` port, for the ROM only, or a second SDRAM); leave it out of the OSD for now and tell me.
- **The SDRAM controller.** `rtl\machine\PPCMac_sdram.sv`, in the memory clock, on the `b_*` side of the crossing: a line request is one 16-halfword burst (or two of eight; the controller's choice, say which), a word request is two halfwords with `SDRAM_DQML/DQMH` from the byte enables so that no read-modify-write is needed; byte order: the byte at the even address is `SDRAM_DQ[15:8]`, so that a 4 MB ROM file written byte by byte reads back as the CPU expects (byte 0 in bits 31-24 of word 0). Refresh at the module's rate; the init sequence at power-up with a `ready` output; a second, lower-priority write port for the ROM upload (byte strobes from `ioctl`, paired into halfwords). Start from a proven MiSTer `sdram.sv` (cite which core's; GPL is fine) and adapt it to this port; state the module geometry it assumes in its header.
- **Clocks.** One PLL from `CLK_50M`: the CPU clock, 65 MHz, in one place as a parameter with 60 and 70 easy to try; the memory clock as the controller's design wants (100 to 130 MHz; `SDRAM_CLK` with the phase the proven controller uses). The crossing tolerates any ratio. Video keeps the template's timing from its own clock as it is now.
- **Time base.** `tb_tick` at the real machine's rate: the 604's time base counts every fourth bus clock, and the 7600's bus is 50 MHz, so 12.5 MHz. A phase accumulator in the machine module (add the rate, tick on the carry) gives it exactly on average from any CPU clock; `TB_HZ` a parameter, 12,500,000. The ROM and the OS time things by it.
- **Interrupts.** `ext_irq` is the level from the machine's interrupt controller stub (Grand Central's registers); for the first bitstream it is 0, the stub reporting nothing pending. The decrementer is the CPU's own.
- **Reset.** The CPU is held in reset while `RESET | status[0] | buttons[1]`, while the SDRAM controller is not ready, and until a ROM has been uploaded (`ioctl_download` falling with the ROM's index); `reset_pc` is `FFF00100`. Without a ROM the CPU stays in reset and the display says so.
- **The debug readout.** `rtl\machine\PPCMac_debug.sv`, fed by the CPU's trace port and the machine: rows of 32 squares on the video output in place of the test pattern (a 1 bright, a 0 dark; 16 by 16 pixels each; no font needed), in this fixed order from the top: the last retired pc; the last retired instruction; the count of retired instructions; the cycle count; the CPU's MSR; the last address on the memory port; a status row (ROM loaded, SDRAM ready, CPU in reset, stuck, the RAM size); the build date. "Stuck" is set when nothing retires for 2^24 cycles. `LED_USER` toggles every 2^20 retired instructions and stays on when stuck. Also a UART transmitter, 115200 8N1, on `UART_TXD`, sending the same rows as hex once a second; it is forty lines, build it; **mine to say** whether I have a serial path to see it, so the display is what the bring-up relies on.
- **The bench runs the same machine.** `core_main.cpp` gets `--machine --rom FILE [--ram MB]`: the CPU, `PPCMac_machine`, the crossing, and the bench's software memory standing in for the SDRAM controller on the `b_*` side (the ROM file placed at its SDRAM offset, the wait states as now). The device stubs are RTL and are simulated as they will run; the lockstep with dingusppc works on this configuration.

## Rules

- SystemVerilog is fine, limited to what Verilator 5.020 and Quartus 17.0 both accept. Keep the RTL clean under Verilator `-Wall` (`make -s lint` in `verilator\`). What Quartus 17 has refused so far: a second read expression on a memory (it becomes flip-flops), byte-enabled writes to a wide array (flip-flops again; `DSPPC604_cache_ram` is eight word RAMs with a write enable each, the shape it infers), a variable part-select of a two-dimensional array (flatten first), `genvar` declared inside the `for`, a generate loop without `generate`/`endgenerate`, every RAM style attribute (`ramstyle = "MLAB"`, `no_rw_check`, the pragma form, the qsf assignment: all ignored), a three-input add written as one expression (two adders in series; write the 3:2 compression and one adder), and a RAM written from registers whose read is combinational (pass-through logic appears; write the read synchronously). Verilator accepts all of these, so lint does not catch them; only a Quartus run does (`quartus_map` alone, in a minute, on a copy of `rtl\` and `syn\` in the scratchpad, answers RAM questions).
- Module and file names carry the CPU model: `DSPPC604_*`. Each later CPU model gets its own version; the machine's modules are `PPCMac_*` under `rtl\machine\`.
- Real hardware outranks every emulator and the manual; of the emulators I trust dingusppc most. The 604 data is two runs on the 7600 (`results_604_run2.csv`) and one on the 7300 (`results_604_7300_of_run1.csv` and the second stage), identical where they overlap.
- Commit your work locally at verified points. Never push. Stage explicit paths (`rtl`, `verilator`, `syn`, `docs`, `PPCMac.sv`, `PPCMac.qsf`, `files.qip`, `README.md`, the resume prompts), never `git add -A`.
- Don't modify anything under `ppctest\`. `sys\` is the MiSTer framework and is never edited. Don't modify the dingusppc tree (the reference library compiles it unmodified; keep it so).
